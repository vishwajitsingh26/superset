## Headline result: stage A is not the problem

Before tracing anything downstream, A's own bounding boxes and extracted
values were checked directly: all 18 region `bbox` fractions were re-rendered
against the actual 1334×991 design PNG using `crop.py`'s exact highlight logic
(margin-inflated crop + inset outline). Every region checked — both KPI cards,
the spending-trend chart, the date pill, the filter row, both tables, the
world map, and recent activity — tightly and correctly bounds its intended
section, with no offset, no wrong-region capture, no source-side clipping.

The values A extracted are also correct: KPI cards read $68,421/-12.5%,
$34,892/-8.7%, $18,230/-15.3%, $8,299/-10.2% (Total/Compute/Storage/
Networking) — exactly the design's real numbers, not the wrong ones the built
dashboard later shows. Spend-by-Account's five percentages (12.5%, 9.8%,
-4.2%, -11.6%, 6.3%) are also read correctly. The date pill's own bbox already
has margin to spare around the full "Apr 1, 2025 - Apr 30, 2025" string — it
is not clipped at the source.

**Every fidelity defect in this run is introduced downstream of A**, in B's
data generation, C's stock/custom decisions, D's chart config, E's grid-width
conversion, F's generated plugin code, or the dashboard-assembly step in
`applier.py`.

## Explicit regression / recurrence / new call-out

Checked against `7aee8684`, `634f6b68`, and `dc2e58c1`:

  worked correctly all three times (`F-high_01/02/03` all succeeded). Neither

  $3,418" instance (§9 there) — now 10-15% off on 3 of 4 cards, plus the new
  `computeTrend.ts` delta-computation bug compounds it into an identical wrong

## Findings, stage by stage

### Stage A — Decompose

No fidelity gap found. See "Headline result" above — all 18 region boxes and
extracted values checked directly against the source design and found
accurate, including specific per-card KPI values/deltas and a full 4-series
colour/axis breakdown for the spending trend.

### Stage B — Bind/build data

- **Per-category KPI values don't reconcile against A's observed figures**
  (only the grand total was calibrated) — Summary #2.
- **All spend-category daily series share one growth shape**, which is what
  makes a first-half/second-half delta split read as ~36.7% on every card
  regardless of category — Summary #3 (contributing cause).
- **Percent-fraction convention correctly followed** (the `634f6b68` #5 fix
  held at the B layer) — not a fault this run.

### Stage C — Resolve

- **`pop_kpi` never evaluated for the KPI cards**, this time because C's own
  reasoning only ever compares against the one candidate A supplied
  (`big_number`), not because A supplied `null`. See regression call-out
  above — this is a deeper, more robust-to-fix version of `634f6b68`'s
  finding.
- Prompt improvements since HEAD (mandatory-question-on-fidelity-loss,
  capability-card judged over self-written description, `same_as` splitting,
  `label_colors`, concrete-CSS requirement, `grid_text`/`custom_text`
  single-vs-multi-line routing) are real and, where checked, worked correctly
  this run.

### Stage D — Configure chart

- **No `customColumnName` set for raw dimension columns** in stock `table`
  configs (`r13`, `r17`) — the mechanism exists
  (`TableChart.tsx:859: config.customColumnName || originalLabel`) and is
  simply never used; metrics get labels automatically via their adhoc-metric
  object, dimensions don't. Confirms, with certainty, what `634f6b68` could
  only tentatively flag.
- **No `columnWidth` override for a percent column in a narrow table card**
  (`r13`) — the mechanism exists, D never sets it, so the auto-sizing
  algorithm clips the "%" suffix.
- **A mechanical repair pass silently reverted two already-correct fields**
  (`r08`/`r09`'s label/icon) while fixing an unrelated flagged issue, by
  regenerating the whole object from a stale `params_hint` template instead
  of patching only what was flagged — Summary #4. The identically-structured
  repair for `r07` did not regress, showing this is inconsistent model
  behavior under repair pressure rather than something the prompt reliably
  causes — but the repair-prompt's own contract (present the model's prior
  output, patch only the flagged field) doesn't currently guard against it.

### Stage E — Layout

- **Filter-widget grid width computed as a direct fraction of the design's
  bbox, with no floor for content-driven text** — causes the date pill's
  truncation (Summary #8c). `E_layout.md` gives no minimum-column guidance
  for `filter`-role regions independent of their measured bbox.
- **Card height budget for `r18` (Recent Activity) doesn't allow for the
  extra body-row the chrome contract forces when an action link has to be
  drawn inside the plugin body** — self-flagged as architecturally
  unavoidable by the model that wrote the plugin, but nothing downstream
  compensates (Summary #9).
- Hosted-child exclusion from `position_json` (`c11`, `c16`, `c17` correctly
  absent from the grid, present only in their wrapper's own params) is
  correct — E did its job here. The bug is one stage later, in `applier.py`
  (Summary #1).

### Stage F — Scaffold plugin

- **`computeTrend.ts`'s delta computation is architecturally wrong for a
  single-bound-period dataset** — splits one period's series at the midpoint
  instead of using a genuine period-over-period comparison, per the prompt's
  own "never trust the headline for delta" instruction with no fallback for
  reading a precomputed delta (Summary #3).
- **`buildQuery.ts` for the spending-trend chart reintroduces a numeric/
  temporal column mismatch through a bespoke `grain` control**, invisible to
  every existing guard because they're keyed to the standard control name
  (Summary #5).
- **The Daily/Weekly/Monthly toggle is inert** — the wrapper sets
  `formData.time_grain_sqla`, the child chart's `buildQuery.ts` only reads
  `formData.grain`; two independently-authored F calls never connected.
  Self-flagged by F's own `review_notes` as a risk, confirmed real.
- **`PctChangeCell.tsx` formats a fraction with bare `.toFixed(1)`**, no ×100
  — the model's own `thinking.md` shows it identifying this exact
  ambiguity and silently resolving it wrong, in violation of the shared
  preamble's "report uncertainty, don't guess silently" rule (Summary #6).
- **World map plugin has no real basemap** — a systemic toolchain gap, not a
  model failure to try harder; F correctly reasoned its way to the right fix
  and was structurally blocked from doing it (Summary #7).
- **Search-filter plugin's `buildQuery.ts` emits zero query objects**,
  because the "wrapper with no data emits no query" rule was applied to a
  standalone grid filter rather than an actual content-hosting wrapper
  (Summary #8b).
- **Badge colour token choice reads paler than the design's solid fills** —
  the "no literal colours" rule was followed correctly; the specific token
  pairing chosen (tint background + saturated icon) just doesn't match a
  solid-fill design (Summary #9, second half).
- Prompt improvements since HEAD (`optionalMetrics.ts` routing,
  `axis_formats` requirement, KPI colour/icon-control requirement, adhoc-
  metric-object requirement) are real and worked correctly this run — no
  metric-null crash, colour/icon controls present and populated.

### Stage G — Visual verify

  anywhere in G's output at all. A third (`r17_table`) gets an unhedged,

- `_cap_unverified_findings` (a real fix, present in code since `634f6b68`,
  demotes severity and annotates findings on unverified regions using the

  present and correctly wired in `visual_verify.py`, but whether its
