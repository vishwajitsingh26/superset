## Explicit regression call-out

The task brief names six recent fixes. Here is what this run shows for each:

- **Chrome-surface regression guard (`_restore_untouched_chrome` in `a_decompose.py`) — working, but narrower than the drift it guards against.**
  A_02 (the repair pass, asked to fix only region 12's `chrome.actions`) redrifted on its own initiative anyway: region 1's `chrome.title` `plain`→`decorated`, region 2's `chrome.surface` `bare`→`card`, and — **not covered by the guard at all** — regions 3–6 lost `stock_candidate: "pop_kpi"`, becoming `null`. I confirmed from `B_01/prompt.md` (what stage B actually received) that the guard *did* revert regions 1 and 2's `chrome` back to A_01's correct reading. It does not touch `stock_candidate`, `same_as`, or `confidence`, which drifted just as unpromptedly. In this run the consequence is real: C's own `C_01/thinking.md` floated `pop_kpi` as worth checking for the KPI cards, then the *final* decision (`C_02`–`C_05`) never mentions `pop_kpi` again — its rationale compares only against `big_number`/`big_number_total`, both much weaker matches, which makes `new_plugin` an easy call to justify without ever pricing the actual best stock candidate. Whether `pop_kpi` could truly have rendered the sparkline is a separate question (worth checking directly against its capability card), but the fact that it was never evaluated in the final plan is a direct, traceable consequence of an unguarded field. **Recommendation: extend `_restore_untouched_chrome`'s pattern (or a parallel guard) to `stock_candidate`, `same_as`, and `confidence`.**

- **Heading subtitle preservation — the fix exists in the prompt/code, and the model didn't follow it; the render then does something the fix doesn't explain.**
  `E_layout.md` explicitly warns about this exact case, and `e_layout.py` has a working post-hoc fixup (`restore_text_content`) that converts a `HEADER` node back to `MARKDOWN` when it matches a multi-line `grid_text` decision by its first line. I confirmed by parsing `E_01/output.json`'s `position_json` that stage E emitted `HEADER-c1` with `meta.text: "Cloud Cost Overview"` only — the subtitle line is simply not in the node at all, i.e. the model did not follow its own prompt's instruction and used `HEADER` for two-line text. The fixup function's matching logic (checked by hand) should catch this on the next line of code the runner executes. But the *rendered* result — `✨Header 1` / `✨Header 2`, twice, neither showing "Cloud Cost Overview" — is not what either the raw `HEADER` node or a correctly-fixed `MARKDOWN` node would produce. I could not resolve this discrepancy from the trace alone (a live Superset credential check to read the dashboard's actual saved `position_json` was blocked by this session's sandboxing). **This is worth a live check of the dashboard's saved `position_json` and of how Superset's `MARKDOWN`/`HEADER` components render an empty or mismatched entry** — it may be a second, distinct bug on top of the confirmed one.

- **Custom-plugin capability cards — working as designed.** `chart_kind`/`capability_card_compared` are populated correctly for every `configure` decision I checked (`stages/c_resolve.py:chart_kind` + `annotate_comparisons`), and C's own reasoning does compare stock thumbnails against the design before choosing `new_plugin` in every case except the `pop_kpi` gap above.

- **Filter-scope `InteractiveChart` enforcement — not exercised meaningfully this run**, because the one filter widget (`r02`) never rendered at all (see §3/Issue 3 above), so its cross-filter scope was never tested end to end.

- **Empty-chart render detection — working.** The `render` block correctly reported `r02_filter`'s failure with the real HTTP/data error, and `confirm_new_plugins`/`plugin_confirmations` correctly tracked every other custom plugin as registered and rendered. Nothing here is a regression; it's the mechanism that caught issue 3 in the first place.

- **`chart_kind`/`plugin_confirmations` trace fields — present and accurate.** Every `configure` decision I spot-checked (`r08`, `r10`, `r11`, `r13`) carries the correct `chart_kind` (`stock`) and a real `capability_card_compared` excerpt; every `new_plugin` decision correctly shows `chart_kind: "custom_new"`.

**New class of gap this run surfaces that the prior review (7aee8684) did not:** a scaffold call whose JSON fails to parse for a reason *other* than a token-budget cutoff gets no second attempt at all (issue 1). The prior review's truncation finding (#4 there) is now handled — `LLMTruncatedError` with an automatic lower-effort retry exists and evidently works for the plugins that did get repaired (`r02`, `r03-r06`, `r07`, `r09`, `r15` each got one). But `run_one`'s `except Exception` branch for every *other* parse failure returns a permanent failure on the first try, which is what actually cost this run its Recent Activity section.

## Findings, stage by stage

### Stage A — Decompose

- **Unguarded field drift in the repair pass (see regression call-out).** `stock_candidate` for regions 3–6 (all four KPI cards) silently reverted from the correct `pop_kpi` to `null` between A_01 and A_02, with no repair note asking for that change and no guard protecting it.
  - *Prompt:* A's prompt already tells the model everything it needs (`stock_candidate`, "a lookup, not a judgement"); the gap is not in what A is told to do on a fresh read, it's that repair passes are regenerations, not patches, and nothing tells the model "leave `stock_candidate` alone unless named."
  - *Validator:* `_restore_untouched_chrome` exists for exactly this class of problem but is scoped to one field.
  - *Code:* fixable by widening that one function's field list.
- Everything else A read (bboxes, chrome for card vs. bare sections, palette, table structure, observed values) checks out well against the design on direct comparison — no other A-stage fidelity gap found.

### Stage B — Bind data

- **The date-range filter's binding names the wrong column** (Issue 3). `B_01`'s binding for `r02_filter` records `"time_column": "usage_date"`, but the SQL view B itself wrote for that binding (`cloud_spend_date_bounds`) is `SELECT MIN(usage_date) AS range_start, MAX(usage_date) AS range_end FROM …` — the view exposes `range_start`/`range_end`, never `usage_date`.
  - *Prompt:* `C_resolve.md` and `F_scaffold_plugin.md` both explicitly describe this exact binding shape ("bound to a one-row view carrying `range_start` and `range_end`; keep that binding" / "Query those two values"). Nothing in `B_design_data.md`/`B_build_data.md` (which I read for their static instructions) tells stage B to record the *view's own* column names rather than the source table's pre-aggregation names for this special one-row binding — worth adding the same explicit instruction there.
  - *Validator:* none catches this. D's self-check ("every column/metric appears in the binding") technically passes — D copied the binding's own (wrong) value verbatim — because nothing cross-checks a binding's claimed column name against the actual SQL it was generated from.
  - *Code:* this is a genuine gap: no step between B and D verifies a binding's column claims against the view's real schema.
- **The KPI cards' dataset carries no temporal column** (Issue 6, half of it). All four `unmapped` entries at D confirm this plainly: "binding has no time_column/time_grain… no real temporal column exists on this dataset." The design's `unusual_treatment` for every one of these regions explicitly calls out an embedded sparkline — B should have bound a daily-or-weekly time series to these regions the same way it did for `r07`'s trend chart, and did not.
  - *Prompt/validator/code:* this reads as a plain miss in B's binding pass rather than something the prompt fails to ask for — `B_design_data.md`'s job is precisely to notice what each region's `implied_data` needs, and region 3's `implied_data` literally says "…plus a short trend of total spend over recent days/weeks."
- **Percent values stored as whole numbers, formatted as fractions** (Issue 5). `pct_change` in both `d2d.cloud_spend_by_day`-family tables (feeding `r10` and `r12`) is generated as e.g. `-15.2`, while C's design-system contract sets `number_formats.percent: ".1%"` — a d3 format that multiplies by 100, assuming a fraction. The two stages never agree on which convention the data uses.
  - *Prompt:* neither `B_design_data.md`/`B_build_data.md` nor `C_resolve.md` states a convention for percent-typed columns (fraction vs. whole number) that the other stage can rely on.
  - *Validator:* none — this renders without error, just 100× wrong, which is exactly the class of defect the prompts elsewhere warn about ("no error, no warning, just the wrong number").
  - *Code:* a mechanical check comparing a `pct_change`-like column's actual value range (e.g. sampled min/max) against the format string's assumption would catch this cheaply.

### Stage C — Resolve

- **`pop_kpi` never evaluated for the KPI cards** (contributes to Issue 6/regression call-out). Confirmed by grepping every C output file: `pop_kpi` appears only in the static registry listing embedded in each prompt, never in any `rationale` or `thumbnail_evidence`. `C_01/thinking.md` raises it, then explicitly talks itself out of the tool call that would confirm or deny it ("given the effort constraints… I can justify skipping the tool call"), and the final decision compares only against `big_number`/`big_number_total`.
  - *Prompt:* `C_resolve.md`'s "Judging A's `stock_candidate`" section assumes A hands C a candidate to confirm or overturn; it has no instruction for what to do when A's candidate is `null` because of upstream drift — C is not told to re-derive candidates from the registry's own category list (`KPI: big_number, big_number_total, bullet, funnel, gauge_chart, pop_kpi`) rather than relying on A's field.
  - *Validator:* none checks that a `new_plugin` decision's `thumbnail_evidence` actually names the closest-fitting registry entry for its category, only that it names *something*.
- **`color_scheme` has no path from the design's measured palette to a stock chart's rendered colours** (Issue 7). The design-system contract's schema (`"color_scheme": "supersetColors | <registered scheme>"`) only accepts a name; C recorded the exact hex palette separately under `design_system.palette`, but nothing in this pipeline registers a new named colour scheme from it, so D has nothing but `"supersetColors"` to put in a stock chart's `color_scheme` control. Confirmed by direct image comparison: `r15` (a custom plugin, which gets a literal `customColors` control D can fill with the exact hexes) matches the design's colours pixel-for-pixel; `r08`/`r11` (stock `pie`) and `r13` (stock `echarts_area`) do not.
  - *Prompt:* this is a genuine architecture gap, not obviously a prompt fix — `C_resolve.md` would need either a mechanism to register a scheme, or an instruction to prefer `new_plugin` (or a custom colour-carrying wrapper) whenever exact brand colours matter and no matching registered scheme exists.
  - *Validator:* none flags "this decision's viz_type has no way to honour `design_system.palette`."
  - *Code:* the actual gap is upstream of any one stage — there's no registration path from a measured palette to a Superset colour scheme at all in this codebase.
- Everything else C decided (the `same_as` splits for `r08`/`r11` vs. `r15`, the `filter_widget` archetype for `r02`, `grid_text` for `r01`, the `chrome_menus` handling) is well-reasoned and, where I could check it against the design, correct.

### Stage D — Configure chart

- D's self-checks and repair loop worked correctly where exercised — `D_04`→`D_06` (region `r03`) is a clean example: the validator caught `time_grain_sqla` set against a non-temporal binding and the repair fixed it properly.
- D's `unmapped` reporting is honest and thorough almost everywhere (icons, colours, sparklines, the "View all" link, the % sign inversion risk on `r15`) — this is the stage doing its job of surfacing what it can't fix rather than papering over it.
- One likely miss, lower confidence: `r10`'s table (`D_13`) shows raw column names (`service_name`, `provider_name`) in the built table, but `r12`'s table (`D_15`) shows clean labels for its *metric* columns ("Total Spend", "% Change") while its *groupby* column (`account_name`) stays raw. This is consistent with `table`'s `column_config`/label override applying to metrics (which carry an explicit `label` in the adhoc-metric object) but not to plain `groupby`/`all_columns` entries unless a column-level override is set — I could not confirm from this checkout whether `table`'s control panel actually exposes a raw-column relabel control that D simply didn't use, versus a genuine capability gap. Worth a quick check against the live control schema before deciding whether this is a D-stage miss or an `unmapped` entry D should have written and didn't.

### Stage E — Layout

- **`HEADER` used for two-line text against the prompt's own explicit instruction** (Issue 2, regression call-out) — see above.
- Otherwise E's handling of the dropped `r14` region is exactly right: `unplaced` is empty (correctly, since nothing was "unplaced" — the decision was dropped upstream), row 4's width underflow is explicitly annotated as "the design's middle card… is missing… not a rounding error," and no phantom grid node was created for it.
- The `ROW-0` width compromise (title flush-left, filter flush-right, gap approximated by unused columns) is a reasonable, clearly-documented trade-off given Superset's ROW primitive has no offset/spacer — not a bug.

### Stage F — Scaffold plugin

- **`custom_activity_feed`'s only generation attempt returned unparseable JSON and got no retry** (Issue 1). `F_05/meta.json` records `"output_is_json": false`, `"error": null` — the call completed without the provider-level error that would trigger `LLMTruncatedError`/`LLMTimeoutError`, so `run_one`'s generic `except Exception` branch caught the `extract_json` failure, returned a permanent `ScaffoldResult(error=...)`, and the runner's `_drop_decision` path took over with no second attempt. Every *other* plugin that needed a repair in this run got one (`r02`/`r03-06`/`r07`/`r09`/`r15` each show a second `F_XX` call). Whether the raw text was actually a `stop_reason=max_tokens` truncation that this call's classifier failed to recognise, or a genuinely malformed-but-complete reply, I could not determine from the recorded metadata (no `stop_reason` field is captured in `meta.json`) — either way, the fix is the same: a parse failure that isn't classified as truncation should still get at least one retry, the way a truncation does.
- **`custom_spend_trend_chart` has a live date-formatting bug** (Issue 4) — "0NaN" on every x-axis tick. Everything else about this chart (stacked bars, legend, series colours, Y axis) matches the design closely; this reads as a targeted component bug (a date value reaching a formatter as something other than what it expects), not a broader plugin failure.
- **`custom_kpi_spend_card` was built without a way to reach its own justification.** C's `rationale` for going custom rather than stock explicitly cites "icon + label + value + coloured delta + embedded sparkline" as the fidelity case for a plugin — but the plugin F actually wrote has no colour control at all (D's `unmapped`: "control panel exposes no colour control for this plugin") and only a generic `iconOption` enum with no brand-logo option, so two of the three things the custom build was justified by (accent colour, real icon) don't work either. This is worth a look at `F_scaffold_plugin.md`'s guidance for KPI-style plugins — it already says "expose a colour control, fall back to a theme token" for the general case; a KPI card whose entire purpose is per-provider branding is exactly the case that rule exists for, and this plugin doesn't have one.

### Stage G — Visual verify

- G's own findings (`r01`, `r02`, `r07`, `r10`, `r12`, `r03`, `r08`, `r13`, `r09`) all check out against direct image comparison — no false positives found.
- **G never mentions `r11_cost_by_environment` anywhere** — not as a finding, not as an omission in `summary`. It is one of the four regions the image budget dropped (`not_verified`, along with `r02` [already known-failed], `r13`, `r15`), and it carries the same defects as its twin `r08` (no legend percentages, wrong colour scheme, an unexplained "All / Inv" toggle the design never draws) — confirmed by cropping the design and comparing against `screenshots/…-chart168.png` myself. - **G's `r13` finding is specific in a way its own prompt says it shouldn't be**, given `r13` was also in `not_verified`.
