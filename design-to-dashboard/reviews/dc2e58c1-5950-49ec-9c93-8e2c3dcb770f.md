# Stage F root-cause + fix — dc2e58c1-5950-49ec-9c93-8e2c3dcb770f

- **Scope:** stage F only — why 8 of 11 plugin builds failed outright in this
  run, and the fix. Not a full fidelity review of the dashboard (see
  [[d2d-fidelity-review-7aee8684]] / [[d2d-fidelity-review-634f6b68]] for that
  kind of pass on other runs).
- **Evidence:** `design-to-dashboard/traces/dc2e58c1-…/F_*/meta.json` (provider
  call records) and `design-to-dashboard/traces/dc2e58c1-….md` (the run's own
  decomposition/binding/resolve narrative), cross-checked against
  `design-to-dashboard/traces/634f6b68-…/F_*/meta.json` as a second data
  point.

## 1. Frequency

| Run | F calls | Provider-level errors | Shape |
|---|---|---|---|
| `dc2e58c1` | 11 | **8** `LLMError: … Reached maximum number of turns (6)` (F_01,02,03,05,06,08,09) + 1 sleep-interrupt (F_10) | 3 succeeded (F_04, F_07, F_11) |
| `634f6b68` | 13 | 0 recorded at the provider level | 1 plugin (`custom_activity_feed`, F_05) came back non-JSON and was dropped with zero retries — a different failure shape (malformed reply, not a turn-budget error), already forwarded to the runner's retry in the *current* code (`LLMMalformedReplyError` was in `run_one`'s retry-eligible except tuple before this fix) |
| `e41b84a7`, `e7a97534`, `53663201` | 0 | — | these three runs never reached stage F (stopped at A/B/C) |

So the turn-budget failure is not a one-off: it is the dominant failure mode
of the one run that hit it hard, and the code path that swallowed it applies
to any run using the `claude_agent_sdk` provider for stage F.

## 2. Root cause (confirmed by reading the code, not inferred from symptoms)

`ClaudeAgentSdkProvider.max_turns` defaulted to the top-level config value
(6) — `superset/design_to_dashboard/llm/factory.py`'s `DEFAULTS["max_turns"]`
— with no per-stage floor the way `max_tokens` (`STAGE_MIN_MAX_TOKENS`) and
`effort` (`STAGE_DEFAULT_EFFORT`) already have for stage F. Stage F's only
tool is `Read`, spent opening the 1-2 attached design images before it can
reason at `effort=xhigh` and then write an entire multi-file plugin into its
final answer (no `Write` tool — everything must fit in the reply). Six turns
is frequently not enough for that combination once a plugin is non-trivial.

When it isn't, the Agent SDK reports `ResultMessage.is_error` and
`agent_sdk.py` raised a **bare `LLMError`**. `f_scaffold.run_one`
(`stages/f_scaffold.py:900-943`) only forwarded three specific error types to
the runner's retry — `LLMTimeoutError`, `LLMTruncatedError`,
`LLMMalformedReplyError` — so a bare `LLMError` fell into the generic
`except Exception` and came back as a **failed `ScaffoldResult` with zero
retries**, indistinguishable from a model that refused outright. This is the
same bug class [[d2d-fidelity-review-634f6b68]] found for a malformed JSON
reply (already fixed in the code as of this session — `LLMMalformedReplyError`
is forwarded) — this run shows it recurring in a different, much more
frequent shape that was never covered.

A bare retry would not have helped here either: the second attempt asks the
identical request with the identical 6-turn budget and spends it on the
identical `Read` calls, so it fails the identical way. Unlike a truncated
reply (whose existing `on_truncated` fallback correctly retries at *lower*
effort), there was no fallback that changed the odds for a spent turn budget.

## 3. Fix implemented

- `LLMMaxTurnsError(LLMError)` (`llm/base.py`) — a typed sibling of
  `LLMTruncatedError`/`LLMMalformedReplyError`, carrying `max_turns`.
- `agent_sdk.py` now recognises the SDK's own "maximum number of turns"
  wording (`_is_max_turns_error`, a pure function so it's unit-testable
  without the `claude_agent_sdk` package) and raises the typed error instead
  of a bare `LLMError`.
- `f_scaffold.run_one` forwards `LLMMaxTurnsError` to the runner's retry,
  alongside the three existing types.
- `runner._retry` gained an `on_max_turns` fallback (mirrors `on_truncated`),
  and a new `_higher_turns_provider` helper (mirrors `_lower_effort_provider`)
  builds a provider at **double** the turn budget, capped at
  `MAX_RETRY_TURNS = 48`. Wired into stage F's build call alongside the
  existing truncation fallback.
- `factory.py` gained `STAGE_MIN_TURNS = {"F": 16}` and a `_resolve_turns`
  resolver (same shape as `_resolve_budget`), plus a `max_turns` override
  parameter on `get_llm_provider`, mirroring how `effort` already works as an
  override for the truncation fallback. Stage F's default turn budget is now
  16 (was 6), configurable per-deployment via
  `stage_models["F"]["max_turns"]` the same way `max_tokens` already is.

So a plugin that still exhausts its (now larger) budget gets one retry at
double the turns before the section is dropped, instead of zero.

Files: `llm/base.py`, `llm/agent_sdk.py`, `llm/factory.py`,
`stages/f_scaffold.py`, `runner.py`, plus new/extended unit tests in
`tests/unit_tests/design_to_dashboard/{llm_agent_sdk_test,llm_factory_test,runner_retry_test,f_scaffold_test}.py`.
All pass; `pre-commit` (mypy, ruff, ruff-format) is clean on every touched
file.

**Why 16, not some other number:** there's no direct "turns used" telemetry
in `meta.json` for a successful call, so this floor is reasoned from the
task shape (1-2 `Read` calls + iterative reasoning before a large final
answer), not measured. The doubling retry (up to 48) is the actual safety
net — if 16 turns out to still be tight for some plugins, the retry recovers
them without needing the floor itself to be exactly right on the first try.
Recommend watching the next few runs' `F_*/meta.json` for "Reached maximum
number of turns" — if it still recurs, raise `STAGE_MIN_TURNS["F"]` (a
one-line config change) rather than reworking the mechanism again.

## 4. Decision — split scaffold-generation vs. repair provider profiles?

**Not implemented, and not recommended yet.** `_repair_broken_plugins` /
`f_scaffold.repair_one` reuse stage F's own provider (same model, `xhigh`
effort, now the same 16-turn floor) for post-hoc TypeScript-compiler-error
patches. This run's one observed repair call (`F_11`: 0 images, 35s, patch
JSON, no error) succeeded quickly and cheaply even at the shared profile —
there is no *failure* evidence pointing at repair specifically, only a
plausible cost argument (repair's task — patch named files against explicit
compiler errors — is narrower than authoring a plugin from a design image,
so it may not need `xhigh` or as many turns). Splitting the profile would
mean adding a second stage key (e.g. `"F_repair"`) through
`STAGE_DEFAULT_EFFORT`/`STAGE_MIN_TURNS`/`stage_models` and threading it
through `_typecheck_and_quarantine` → `_repair_broken_plugins` →
`provider_for`. Worth doing as a follow-up cost optimization once there's
more than one data point on repair's actual turn/token usage; not worth the
config-surface growth on a single successful sample.

## 5. Plan — shifting boilerplate off free-hand LLM authorship

**Not implemented this pass; a concrete follow-up.** The pipeline already
has a deterministic-templating layer, `plugin_skeleton.py`
(`assets/plugin-skeleton/`, `assets/reference-plugin/`), which mirrors what
the Superset community itself uses to scaffold a plugin —
`@superset-ui/generator-superset` via `yo @superset-ui/superset`
(`docs/developer_docs/contributing/howtos.md`) — for the mechanical pieces:
package name, `index.ts`, the `ChartPlugin` subclass, the
import/registration lines. Stage F's prompt/response contract still asks the
model to freehand-author *every* file's full contents in one JSON reply,
including those mechanical parts, which is both wasted reasoning (they're
the same shape every time) and part of what fills the turn/token budget that
bug #2 above was tuned around.

Proposed follow-up, in order of effort:
1. Confirm `plugin_skeleton.render()`'s current coverage against a sample of
   this run's actual generated files (which of `package.json`, `index.ts`,
   `buildQuery.ts`, `controlPanel.ts`, `transformProps.ts`, the component are
   already templated vs. still fully freehand).
2. For whichever boilerplate isn't yet templated, extend `render()` to
   produce it and shrink stage F's prompt/schema so the model returns only
   the design-specific files (the component's JSX/layout, `transformProps`'s
   data mapping, any custom controls) — this is a schema and prompt change to
   `F_scaffold_plugin.md`, not just a code change, so it needs a prompt-side
   pass too.
3. Re-measure `thinking_chars`/turns on a rebuilt sample to confirm the
   narrower scope actually reduces the pressure that caused bug #2, rather
   than assuming it will.
